## Часть 2 — namespaces


Сначала по флагам для unshare:

-pid — изолирует дерево процессов. Внутри запускается новая нумерация с 1, а процессы реального хоста скрываются.   
--uts — изолирует системное имя компьютера (hostname) и домен. Позволяет процессу задать собственное имя хоста без изменения имени реальной машины.   
--mount — изолирует таблицу точек монтирования файловой системы. Все операции подключения каталогов (mount / umount) будут видны только внутри этого окружения.   
--net — изолирует сетевой стек. Процесс получает персональное чистое сетевое пространство со своим набором интерфейсов, IP-адресов, таблицей маршрутизации и портами.   
--ipc — изолирует механизмы межпроцессного взаимодействия. Не дает процессу заглянуть в семафоры, очереди сообщений и разделяемую память (shared memory) чужих программ на хосте.   
--user — изолирует идентификаторы пользователей (UID) и групп (GID). Разрешает иметь одни права внутри окружения и другие на реальном компьютере.   
--map-root-user — настраивает таблицу соответствия пользователей для User Namespace. Делает текущего непривилегированного пользователя хоста суперпользователем root (UID 0) внутри контейнера.   
--mount-proc — автоматически создает и подключает персональную виртуальную файловую систему /proc для нового PID namespace прямо перед запуском программы (чтобы утилиты вроде ps сразу видели список процессов без ручного монтирования).   
--fork — заставляет unshare запустить целевую программу через системный вызов fork() как отдельный дочерний процесс. По правилам ядра Linux только дочерний процесс может стать PID 1 в новом пространстве PID.

## Часть 3 — cgroups

Создаём подгруппу для сервиса в cgroups v2
sudo mkdir -p /sys/fs/cgroup/mylab

Разрешаем дочерним папкам управлять памятью
echo "+cpu +memory +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

Ставим лимит 50 МБ (50 * 1024 * 1024 байт)
echo "52428800" | sudo tee /sys/fs/cgroup/mylab/memory.max

Запускаем сервис в фоне
./api

Добавляем PID запущенного сервиса в cgroup
echo PID | sudo tee /sys/fs/cgroup/mylab/cgroup.procs

Запрашиваем 80 МБ при лимите в 50 МБ (вызываем OOM-killer)
curl "http://localhost:8080/eat?mb=80"

Смотрим счётчик OOM (oom_kill должен стать равен 1)
cat /sys/fs/cgroup/mylab/memory.events



## Часть 4 — права

Оставь процессу только нужный минимум:

- сбрось лишние capabilities и покажи, что привилегированное действие (например, смена системного времени) больше не проходит;
- навесь seccomp-профиль и покажи, что заблокированный системный вызов отклоняется.

## Часть 5 — Собери свой Docker

Собери все команды из частей 2–4 в один скрипт (например, `mydocker.sh`), который одной командой запускает `api` в своих namespaces, с cgroup-лимитами и урезанными правами. Проверь, что сервис поднимается и `/health` отвечает.

Теперь запусти тот же сервис через `docker run` и сравни с запуском своего скрипта: что совпадает, чего в твоём скрипте нет и что Docker делает сверх него. Сведи сравнение в README.

## Часть 6 — Образы

Твоему скрипту не хватало готовой файловой системы — её и даёт образ.

- Напиши Dockerfile для `api` и собери образ.
- Сделай multi-stage-сборку с минимальной базой (для Go подойдёт `scratch` или distroless). Сравни размер, число слоёв и что переиспользовалось из кэша при повторной сборке.
- Запиши файл внутрь контейнера, пересоздай контейнер — файл пропал. Повтори с томом — файл остался.

## Часть 7 — Когда контейнера мало

Запусти образ под gVisor (`runsc`) и сравни его изоляцию с обычным Docker и своим скриптом. Разберись, чем gVisor устроен иначе и почему его считают более изолированным.
