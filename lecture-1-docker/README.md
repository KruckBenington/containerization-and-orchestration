## Часть 2 — namespaces


Сначала по флагам для unshare:

-pid — изолирует дерево процессов. Внутри запускается новая нумерация с 1, а процессы реального хоста скрываются.   
--uts — изолирует системное имя компьютера (hostname) и домен. Позволяет процессу задать собственное имя хоста без изменения имени реальной машины.   
--mount — изолирует таблицу точек монтирования файловой системы. Все операции подключения каталогов (mount / umount) будут видны только внутри этого окружения.   
--net — изолирует сетевой стек. Процесс получает персональное чистое сетевое пространство со своим набором интерфейсов, IP-адресов, таблицей маршрутизации и портами.   
--ipc — изолирует механизмы межпроцессного взаимодействия. Не дает процессу заглянуть в семафоры, очереди сообщений и разделяемую память (shared memory) чужих программ на хосте.   
--user — изолирует идентификаторы пользователей (UID) и групп (GID). Разрешает иметь одни права внутри окружения и другие на реальном компьютере.   
--map-root-user — настраивает таблицу соответствия пользователей для User Namespace. Делает текущего непривилегированного пользователя хоста суперпользователем root (UID 0) внутри контейнера.   
--mount-proc — автоматически создает и подключает персональную виртуальную файловую систему /proc для нового PID namespace прямо перед запуском программы (чтобы утилиты вроде ps сразу видели список процессов без ручного монтирования).   
--fork — заставляет unshare запустить целевую программу через системный вызов fork() как отдельный дочерний процесс. По правилам ядра Linux только дочерний процесс может стать PID 1 в новом пространстве PID.

## Часть 3 — cgroups

Создаём подгруппу для сервиса в cgroups v2
sudo mkdir -p /sys/fs/cgroup/mylab

Разрешаем дочерним папкам управлять памятью
echo "+cpu +memory +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

Ставим лимит 50 МБ (50 * 1024 * 1024 байт)
echo "52428800" | sudo tee /sys/fs/cgroup/mylab/memory.max

Запускаем сервис в фоне
./api

Добавляем PID запущенного сервиса в cgroup
echo PID | sudo tee /sys/fs/cgroup/mylab/cgroup.procs

Запрашиваем 80 МБ при лимите в 50 МБ (вызываем OOM-killer)
curl "http://localhost:8080/eat?mb=80"

Смотрим счётчик OOM (oom_kill должен стать равен 1)
cat /sys/fs/cgroup/mylab/memory.events

-----

Задаём квоту: 50 000 мкс из периода 100 000 мкс (ровно 0.5 ядра = 50% CPU)
echo "50000 100000" | sudo tee /sys/fs/cgroup/mylab/cpu.max

Запускаем сервис в фоне
./api &

Привязываем PID сервиса к нашей cgroup
echo $(pgrep -n api) | sudo tee /sys/fs/cgroup/mylab/cgroup.procs

Нагружаем процессор на 100% бесконечным циклом через ручку /burn
curl "http://localhost:8080/burn" &

Смотрим статистику троттлинга ядра (счётчики nr_throttled и throttled_usec будут расти)

## Часть 4 — права

Запускаем сервис ./api от root в фоне, отобрав у него право менять время (cap_sys_time)
sudo capsh --drop=cap_sys_time -- -c "./api" &

Входим в контекст запущенного ./api через nsenter и пытаемся изменить дату (получаем: date: cannot set date: Operation not permitted)
sudo nsenter -t $(pgrep -n api) -a capsh --drop=cap_sys_time -- -c "date -s '2027-01-01 00:00:00'"


Создаем конфиг seccomp.json с запретом сетевого системного вызова listen (нужен для сдачи)
cat << 'EOF' > seccomp.json
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    {
      "names": ["listen"],
      "action": "SCMP_ACT_KILL"
    }
  ]
}
EOF

Запускаем ./api с фильтром Seccomp и ловим отказ ядра (получаем: Bad system call (core dumped))
systemd-run --user --wait --pipe -p SystemCallFilter=~listen ./api


## Часть 5 — Собери свой Docker


собрал скрипт

docker run -d --name api-docker -p 8080:8080 -v $(pwd):/app -w /app ubuntu ./api

Что совпадает:

    Оба используют ядро Linux и те же самые механизмы: namespaces (PID, mount, net, uts, ipc, user) для изоляции видимости и Cgroups v2 (memory.max, cpu.max, pids.max) для ограничения ресурсов.   

В обоих случаях внутри контейнера процесс выполняется как PID 1.   

Чего не хватает нашему скрипту:

    Файловой системы (образа): наш скрипт использует корневую файловую систему хоста напрямую; в нём нет изоляции через overlayfs и pivot_root.   

Автоматической сети: Docker сам создаёт виртуальный сетевой кабель (veth-пару), подключает его к мосту docker0 и настраивает iptables/nftables для проброса портов -p 8080:8080. В mydocker.sh нам приходилось стучаться через nsenter.  


   

## Часть 6 — Образы

В этой части я упаковал написанный Go-сервис api в Docker, проверил оптимизацию образов через multi-stage сборку и на практике протестировал, как работают тома по сравнению со стандартным слоем контейнера.   

1. Сборка образов: обычный vs Multi-stage

Сначала я написал базовый одноэтапный Dockerfile.heavy на базе golang:1.22, где исходный код собирается и запускается прямо в среде компилятора:   

    Получившийся образ api:heavy весит около 850 MB и состоит из 12 слоёв в RootFS. Это произошло из-за того, что в образ попали вся ОС Debian, Go SDK, кэш зависимостей и стандартные утилиты.   

Затем я сделал multi-stage сборку в основном Dockerfile с минимальной базой scratch:   

    На первом этапе (builder) бинарник собирается со CGO_ENABLED=0, а на финальном этапе в абсолютно пустой образ scratch копируется исключительно скомпилированный бинарник.   

Итоговый образ api:slim весит всего ~12 MB (размер упал больше чем на 98%), а в RootFS остался ровно 1 слой.   

Разницу в размерах образов я зафиксировал командой docker images | grep api (скриншот приложен к отчету).   

2. Кэширование сборщика (BuildKit)

Я протестировал поведение кэша при повторной сборке docker build -t api:slim .:   

    При сборке без правок все этапы помечаются как CACHED, билд проходит мгновенно.   

Когда я изменил файл через touch main.go, на строчке COPY . . кэш сбросился из-за изменившегося хэша файла, и шаг компиляции RUN CGO_ENABLED=0 go build... запустился заново, в то время как слои базового образа взялись из кэша.   

3. Эфемерность контейнера vs Persistent Volumes
   

Я проверил, как контейнер обращается с данными с томом и без него:   

    Без тома (эфемерный writable layer):

       

Я запустил контейнер api:heavy, зашел внутрь и записал файл в его файловую систему (sh -c "echo 'secret data' > /app/data.txt"). После этого я удалил контейнер через docker rm -f и пересоздал его заново. Попытка прочитать файл выдала No such file or directory — все изменения пишутся в верхний временный слой OverlayFS и стираются вместе с удалением контейнера.   

С томом (Volume):

Я запустил контейнер с монтированием именованного тома -v api-volume:/app/storage и записал файл в папку /app/storage/data.txt. Затем полностью удалил контейнер и поднял совершенно новый контейнер, примонтировав тот же volume api-volume. Файл остался на месте и успешно прочитался (persisted data), потому что том хранится на хосте отдельно от контейнера и не зависит от его жизненного цикла.  

 

## Часть 7 — Когда контейнера мало

В этой части я протестировал запуск сервиса в изолированной песочнице gVisor (`runsc`), исследовал механизм его работы и на практике сравнил уровень изоляции со стандартным Docker и моим скриптом `mydocker.sh`.

---

### 1. Что было сделано

1. **Установка и настройка рантайма:**
   Я установил пакет `runsc`, зарегистрировал его как доступный рантайм в Docker daemon (`sudo runsc install && sudo systemctl restart docker`) и убедился через `docker info`, что `runsc` распознаётся системой.

2. **Запуск сервиса:**
   Я запустил контейнер с собранным сервисом `api:heavy` под управлением gVisor:
   ```bash
   sudo docker run -d --name api-gvisor --runtime=runsc -p 8080:8080 api:heavy
   curl http://localhost:8080/health
   sudo docker rm -f api-gvisor

Сервис штатно поднялся и вернул ответ ok.

    Сравнение видимости ядра:
    Я сравнил поведение системы при запросе версии ядра:

        В обычном Docker (runc): команда sudo docker run --rm ubuntu uname -r вернула точную версию ядра хоста (6.8.0-generic), так как процесс выполняется непосредственно на хостовом ядре.

        Под gVisor (runsc): команда sudo docker run --rm --runtime=runsc ubuntu uname -r вернула фиксированную виртуальную версию (4.4.0), скрывая реальные характеристики хостовой системы.

2. В чём архитектурное отличие gVisor

    Обычный Docker и мой скрипт (runc / mydocker.sh):
    Изолируют окружение за счёт механизмов namespaces (видимость процессов, сети, монтирований) и cgroups (лимиты ресурсов). При этом отдельного ядра внутри нет: любые системные вызовы (syscalls) приложения направляются напрямую в ядро хоста.

    gVisor (runsc):
    Устанавливает между приложением и хостом защитную прослойку — user-space микроядро Sentry, написанное на Go. Приложение помещается в песочницу, а все его системные вызовы перехватываются и эмулируются Sentry. Реальное ядро хоста изолировано от прямого взаимодействия с контейнером.

3. Сравнение подходов

    Скрипт mydocker.sh: запускает процесс в общих namespaces ядра хоста с ручной настройкой cgroups. Системные вызовы идут в ядро хоста напрямую без фильтрации.

    Обычный Docker (runc): изолирует процесс через namespaces, cgroups и базовый профиль seccomp/capabilities. Запросы всё ещё идут в хостовое ядро, но опасные syscalls блокируются по белому списку.

    Docker + gVisor (runsc): полностью блокирует прямой доступ к ядру хоста. Системные вызовы обрабатываются в Sentry, обеспечивая уровень защиты, близкий к виртуальным машинам, но без их накладных расходов.

4. Что всегда остаётся общим с хостом и почему это предел изоляции

    Что остаётся общим:
    В стандартном контейнере (runc) и скрипте mydocker.sh с хостом всегда остаётся общее монолитное ядро Linux. Планировщик задач, работа с памятью, стек сетевых драйверов и код обработки системных вызовов едины для всех контейнеров и хоста.

    Почему это фундаментальный предел контейнерной изоляции:
    Поскольку системные вызовы обрабатываются ядром хоста напрямую, любая уязвимость в коде ядра (0-day баг, ошибка в драйвере или privilege escalation) позволяет атакующему выйти за пределы контейнера (container escape) и захватить управление сервером. Стандартная контейнеризация предназначена для доверенного кода; для запуска потенциально враждебного или чужого кода необходима изоляция ядра (gVisor).
